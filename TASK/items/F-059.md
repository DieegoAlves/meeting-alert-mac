# F-059 — App pede login do Google repetidamente (loop de reconexão)

## F-059 | categoria: auth/persistência | severidade: crítica | status: fixed
- Telas: `Sources/Auth/GoogleAuth.swift`, `Sources/Auth/FileCredentialStore.swift` (novo), `Sources/Core/AuthStatus.swift` (novo), `Sources/Sync/CalendarSyncService.swift`, `Sources/Prefs/PreferencesView.swift`.
- Sintoma (Diego): "o app fica pedindo pra logar no Google de novo e de novo — já loguei várias vezes e ele continua pedindo." A cada relançamento/rebuild o fluxo OAuth reabre no browser.

## Causa RAIZ (confirmada)
O app é distribuído **assinado ad-hoc** (`codesign --sign -`, **sem Team ID**). O ACL de um item do **Keychain** é atrelado à identidade de assinatura que o criou; **todo rebuild gera um novo cdhash**, então o binário recém-assinado **não consegue mais ler** o item gravado pela build anterior — `SecItemCopyMatching` volta `errSecItemNotFound`/`errSecInteractionNotAllowed`, o `try?` engole o erro, `isAuthorized` lê **false** e `startOAuthIfNeeded()` reabre o browser **a cada launch**. Isso vale para o **refresh token** E para o **client secret** — daí o último erro registrado ser exatamente `HTTP 400 invalid_request — client_secret is missing` (o secret gravado no Keychain sumiu no rebuild seguinte).

Prova medida (ad-hoc, sem Team ID):
- Uma mudança real de código muda o cdhash: `24a89817…` (build X) → `7571161c…` (build revertido). Com Keychain, o ACL quebra nessa transição.
- `codesign -dvvv` → `Signature=adhoc`, `TeamIdentifier=not set`.

A nota operacional da F-058 já tinha visto esse mecanismo, mas o classificou como "não é bug de produto". Errado: no dev-loop do Diego (rebuilds constantes) é **o** bug. F-059 corrige na raiz.

## Correção (root) — FIXED
1. **Store em arquivo, não Keychain.** Novo `FileCredentialStore`: grava refresh token + client secret em `credentials.json` (mapa `{conta: valor}`) no **Application Support** (`AppPaths.appSupportDirectory`), escrito atômico com permissão **0600** (dono lê/grava). O diretório é **keyed por bundle id**, não pela assinatura — sobrevive a rebuild/re-assinatura ad-hoc exatamente como `preferences.json`/`events.json` já sobrevivem.
2. **Migração transparente.** `CredentialStore.loadString` lê o arquivo; se vazio, tenta o Keychain legado, migra o valor para o arquivo e apaga a cópia do Keychain (best-effort — num binário ad-hoc já re-assinado a leitura do Keychain pode falhar; aí não há o que migrar e reautentica-se UMA vez). `GoogleAuth` passou a usar `CredentialStore.*` em todos os pontos (refresh token e client secret).
3. **Refresh silencioso preservado.** `signIn()` (browser) só é chamado em `validAccessToken()` quando **não há** refresh token no store; com token presente, sempre segue o caminho de refresh no endpoint de token — nunca reabre o browser. Só um `invalid_grant`/401 (refresh token realmente morto) apaga a credencial e exige novo login — UMA vez, sem loop.
4. **`--identifier` fixo no codesign.** README, README-scaffold e `scripts/measure-footprint.sh` passam `--identifier com.disco-tec.MeetingAlert` (identidade de assinatura estável; defesa em profundidade).
5. **Status na Preferências.** Nova surface `AuthStatusCenter` (Core) + linha em Preferências → Google OAuth: **"Conectado como <email> · token válido até HH:MM · refresh OK/erro"** (email = id do calendário primário, publicado pelo Sync; validade/refresh publicados pelo Auth). Torna visível que o login persistiu e o refresh está funcionando.

## Auditoria dos gatilhos de `signIn` (item 4 da tarefa)
- `startOAuthIfNeeded()` — gated por `!isAuthorized` (agora true de forma estável). OK.
- `connectGoogle()` — só via menu/ação explícita do usuário. OK.
- `validAccessToken()` — só chama `signIn()` sem refresh token. OK.
- `syncNow()` — faz `guard isAuthorized` e NÃO abre browser em falha de refresh/sync. OK.
- Concorrência: `GoogleAuth` é `actor` + flag `signingIn` serializa sign-ins simultâneos num único ponto. OK.
Nada chama `signIn` incondicionalmente por sync/save/rede.

## Validação
- `swift build -c release` limpo; bundle + ad-hoc sign OK.
- **V1 (raiz):** escrito `credentials.json` (dummy) no container → rebuild real (cdhash `24a89817` ≠ `7571161c`) + re-assinatura → arquivo **byte-idêntico e legível** (sha256 inalterado, perms 600). Um item de Keychain estaria INACESSÍVEL nesse ponto.
- **V2 (anti-loop):** com o token no arquivo, **quit+relaunch 3×** → em todas o app leu o token (sem re-gravar) e **abriu ZERO OAuth no browser** (`OAuth authorize URL` ausente no log). Token não foi apagado.
- **Silent refresh (b):** caminho de código garante refresh sem browser quando há refresh token; validação end-to-end com a conta real do Diego pendente do login único (ver abaixo) — não é possível autenticar no Google pelo agente.
