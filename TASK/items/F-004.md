- Esperado: entender ONDE vivem os 20 MB reais e separar piso inevitável de gordura de app.
- Observado — os 20 MB reais por categoria (footprint idle, coluna Dirty):
  ```
  MALLOC_SMALL (heap)   12 MB   runtime Swift/ObjC + grafo AppKit/SwiftUI/Foundation (NÃO dados do app)
  __DATA_DIRTY          2.1 MB  globais graváveis das dylibs linkadas
  __DATA                1.5 MB  mais dados graváveis de dylib
  MALLOC metadata       1.1 MB  bookkeeping do alocador
  page table            641 KB  page tables do processo
  CoreUI image data     480 KB  backing de assets de UI do sistema
  untagged VM_ALLOCATE  400 KB  anônimo diverso
  __AUTH                381 KB  segmento de ponteiros assinados (arm64e)
  MALLOC_TINY           288 KB  heap pequeno
  (resto somado)       <1.5 MB  CoreAnimation, stacks, IOAccelerator…
  TOTAL phys_footprint  ~20 MB  PASSA (<30)
  ```
  Piso vs gordura: o piso AppKit+SwiftUI medido como phys_footprint É praticamente os 20 MB inteiros (MALLOC_SMALL dominado pelo runtime, não por dados do app; cache de eventos é um JSON de ≤7d+amanhã). Binário próprio contribui ~nada (`__TEXT` 464K residente). **Não há piso >30 MB na métrica do budget.** No RSS o piso É ~55–62 MB e é largamente inevitável: linkar SwiftUI(36 regiões)+AppKit(17) mapeia ~40 MB de páginas COW compartilhadas do dyld shared cache (`__OBJC_RO` 39.4M, `__AUTH_CONST` 28.3M, `__DATA_CONST` 15.9M residentes) — compartilhadas com todo app, só some largando SwiftUI (AppKit puro → ~13 MB RSS, research/03 §1). Mas RSS não é o budget → irrelevante pro veredito.
  Único desvio real de código (opcional): MenuBarController.swift:51-56 cria `NSPopover` + `NSHostingController(rootView: MenuBarView(...))` EAGER no `install()` (launch) e retém pra vida toda; research/03:346-353 (§6.5) manda criar lazy e `contentViewController = nil` no `popoverDidClose`. History/Prefs já são sob-demanda corretamente (HistoryWindowController.swift:18-41 ; PreferencesWindowController open-on-notification) — só o popover destoa.
- Custo pro usuário: nenhum hoje (budget já passa). Otimizar o popover pra lazy economiza fração dos 12 MB de heap — ganho pequeno, o app passa de qualquer jeito.
- (resolvedor) Correção: Criado `makePopover() -> NSPopover` em MenuBarController; toda a construção de `NSPopover` + `NSHostingController` movida para este método (lazy no 1º `handleClick`). `install()` não aloca mais o hosting controller no launch. Nota: `contentViewController` não é zerado no `popoverDidClose` (o hosting controller é retido para evitar recriação a cada abertura — trade-off menor contra o ganho de memória do lazy init inicial).
