# F-060 — 403 "insufficient authentication scopes" após conectar (calendarList.list negado)

## F-060 | categoria: auth/scope | severidade: crítica | status: fixed
- Telas: `Sources/Auth/GoogleAuth.swift`, `Sources/Sync/GoogleCalendarAPI.swift`, `Sources/Sync/CalendarSyncService.swift`.
- Sintoma (Diego): após colar o Client Secret e conectar, o Google retorna **"Acesso negado pelo Google: Request had insufficient authentication scopes."** (HTTP 403 `insufficientPermissions`). Nenhum evento aparece.

## Causa RAIZ (confirmada empiricamente)
O escopo pedido na autorização era **`https://www.googleapis.com/auth/calendar.events.readonly`** (GoogleAuth.swift:125). Esse escopo concede **apenas leitura de eventos** — NÃO concede `calendarList`. A **F-053** introduziu a chamada `api.fetchCalendarList()` (`GET /users/me/calendarList`) como a **PRIMEIRA** requisição de todo `runSyncPass()` (CalendarSyncService.swift:191), mas **o escopo nunca foi alargado** quando essa chamada foi adicionada. Resultado: `calendarList.list` → 403 `insufficientPermissions` ("Request had insufficient authentication scopes") → mapeado para `CalendarAPIError.forbidden` → a mensagem exata que o Diego viu.

**Qual chamada falhou:** `calendarList.list` (a primeira do ciclo), com header `Authorization: Bearer <token de escopo events.readonly>`. `events.list` nunca chegou a rodar.

**Token velho (prova medida):** o refresh token que o Diego já tinha fora concedido sob o escopo **antigo estreito**. Refresh tokens carregam o escopo do consentimento ORIGINAL — então mesmo após alargar o escopo pedido, um refresh devolvia token ainda em `events.readonly`. O novo build, ao dar refresh no token real do Diego, recebeu de volta do Google o campo `"scope": "https://www.googleapis.com/auth/calendar.events.readonly"` — confirmando a raiz — e o detector novo descartou a credencial e exigiu reconexão (SyncStatus gravado: *"Escopo insuficiente (…calendar.events.readonly). Reconecte em 'Conectar Google' para conceder calendar.readonly."*).

## Correção (root) — FIXED
1. **Escopo alargado.** `GoogleAuth.scope` = `https://www.googleapis.com/auth/calendar.readonly` — cobre `calendarList.list` **E** `events.list` (leitura) com um único grant. F-059 não havia mexido no `scope` param; ele só nunca foi alargado na F-053.
2. **Log + verificação do escopo concedido.** `TokenResponse` passou a decodificar `scope`; logamos o escopo concedido na troca de código e no refresh e comparamos com o necessário. Se o escopo concedido não cobre `calendarList` (`scopeCoversCalendarList`), o token é tratado como insuficiente.
3. **Descarte automático de token velho.** No `refreshAccessToken`, se o escopo concedido é estreito, descartamos `credentials.json` (refresh token), publicamos refresh=erro e forçamos reconsentimento — UMA vez. É a remediação automática do token estreito do Diego.
4. **Consentimento fresco.** URL de autorização já usava `prompt=consent`; adicionado `include_granted_scopes=true` para o Google mesclar/reconceder com o escopo alargado.
5. **403 `insufficientPermissions` na API.** Novo `CalendarAPIError.insufficientScope`; `GoogleCalendarAPI.get` classifica o 403 por `reason == insufficientPermissions` (ou mensagem "insufficient authentication scopes"/"insufficient permission") em vez de tratá-lo como rate-limit. Em `syncNow`, ao receber isso, o app **LIMPA a credencial** (`auth.signOut()` — revoga best-effort + status "desconectado") e grava mensagem acionável "Reconecte em 'Conectar Google'" no `SyncStatusCenter` → visível em Preferências. Nunca falha em silêncio.

## Validação
- `swift build -c release` verde; bundle + assinatura ad-hoc OK (`Identifier=com.disco-tec.MeetingAlert`, `Signature=adhoc`).
- **Escopo no binário entregue:** `strings` do binário mostra `calendar.readonly` (+ conjunto de grants de calendarList) e **NÃO** contém mais `calendar.events.readonly`. Raiz corrigida no app que roda.
- **Detector de token velho (end-to-end, conta REAL do Diego):** ao relançar o novo build, o refresh do token existente devolveu `scope=calendar.events.readonly`; o app descartou o refresh token (`credentials.json` → só `google.client_secret`, `hasRefreshToken=false`) e gravou a mensagem de reconexão. Comprova raiz + remediação + "nunca em silêncio".
- **Consentimento fresco iniciado:** novo relançamento (agora não-autorizado) abriu o fluxo de consentimento — servidor loopback ouvindo em `127.0.0.1:<efêmero>`, sem erro registrado — aguardando o Diego concluir no browser com o escopo alargado.
- **Client secret preservado:** `credentials.json` (0600) mantém `google.client_secret` — Diego NÃO precisa recolar o secret.
- **F-059 intacto:** o file-store (`FileCredentialStore`/`CredentialStore`), o gate `isAuthorized` lido do arquivo e o refresh silencioso não foram alterados; o único delete novo é o descarte deliberado do token de escopo insuficiente. `credentials.json` sobreviveu quit+relaunch (0600). O teste "3× relaunch sem OAuth" só passa com um token SAUDÁVEL (escopo largo), que existe após a reconexão única — a persistência em si segue valendo.

## Ação necessária do Diego (login único)
**Sim, reconectar UMA vez.** O token que ele tinha fora concedido no escopo estreito e foi descartado automaticamente. Ele deve concluir o consentimento do Google (o browser já foi aberto pelo app; senão, Preferências → **Conectar Google**) — agora com `calendar.readonly`. A partir daí `calendarList.list` e `events.list` retornam 200, a agenda aparece, e o token largo persiste em `credentials.json` (sobrevive a rebuilds, F-059). O Client Secret já está salvo — não precisa recolar.
